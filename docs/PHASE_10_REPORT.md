## 0. 비전문가용 한 줄 요약

**지금 몇 % 나갔고, 얼마를 기성으로 청구할 수 있는지 보여줍니다.**

§37 이 못박은 문장이 이 단계의 전부입니다.

> "기성가능액 ≠ 실제 제출 기성 으로 구분한다.
>  실제 기성 제출은 본사 승인이 필요하다."

그래서 **초안과 확정을 구조적으로 갈라놨습니다.**

- **기성가능액(초안)** 은 저장되지 않습니다. 부를 때마다 지금 값을 다시 계산합니다.
- **실제 제출 기성** 은 본사만 확정할 수 있고, **확정하는 순간을 그대로 얼려 둡니다** (§38).
  나중에 원본이 바뀌어도 제출한 기성은 그대로입니다.
- 초안과 **다른 금액을 제출하려면 사유가 반드시 있어야 합니다.** DB 가 강제합니다.

여기 나오는 금액은 전부 **계약금액**입니다. 내부 원가(노무비·장비비·단가)가 아닙니다.
계약단가는 §44 대로 현장관리자도 볼 수 있고, 내부 원가는 서버가 애초에 내려주지 않습니다 (§29).

## 1. 이번에 구현한 기능

### 1.1 §36 공정률 — 두 가지 + 보조지표

```
물량 공정률 = 누적 완료 계약수량 ÷ 전체 계약수량
금액 공정률 = 누적 시공 인정금액 ÷ 현재 계약금액
```

**기준을 숨기지 않습니다.** 계약수량이 없어 계획심도로 대신 계산했다면 그 사실을 함께 냅니다.

| 기준값 | 뜻 |
|---|---|
| `CONTRACT_QUANTITY` | 계약수량 기준 (정상) |
| `DESIGN_DEPTH` | 계약수량이 없어 계획심도로 계산 |
| `CONTRACT_AMOUNT` | 계약금액 기준 (정상) |
| `HOLE_CONTRACT_AMOUNT` | 계약이 아직 등록되지 않아 천공 계약금액 합계로 계산 |
| `NONE` | 기준이 되는 값이 없음 |

§36 이 요구한 보조지표도 냅니다.

- **공수 기준** — 완료 공수 / 전체 공수
- **총 천공연장 기준** — 실제심도가 있으면 실제를 씁니다
- **지층별 천공량** — 지층별 완료 연장과 비율
- (추가) **투입 공수** — PHASE 8 출력일보 누계

> 지층별 실적은 **계획 지층 기준**입니다. 지층별 실제 실적은 따로 받지 않습니다.
> 그래서 `by_ground_type_basis: "PLANNED_LENGTH"` 를 함께 냅니다. 기준을 감추지 않습니다.

### 1.2 §37 기성가능액 (초안)

완료된 HOLE_MASTER 기준으로 계산합니다.

```
기성가능액 = Σ (완료 천공의 계약수량 × 계약단가)
             단, 이미 앞 회차에 들어간 공은 뺀다
```

- **저장하지 않습니다.** 조회만으로는 아무것도 만들어지지 않습니다 (§11 임의 확정 금지).
- **공별 계산 근거**를 함께 냅니다. 어느 공이 얼마인지 사람이 확인할 수 있습니다 (§46).
- **계약단가가 없는 공을 0원으로 만들지 않습니다.** 빠진 공수를 WARN 으로 알립니다.
- 앞 회차 누계와 합계도 같이 냅니다.

### 1.3 §37 실제 제출 기성 — 본사 승인

```
[초안 조회]  →  [회차 만들기]  →  [제출]  →  [승인 / 반려]
  누구나          본사            본사       본사
```

| 칸 | 뜻 |
|---|---|
| `draft_amount` | 기성가능액 (만들 때의 계산값) |
| `submitted_amount` | **실제 제출 기성** |
| `adjust_reason` | 둘이 다르면 왜 다른지. **없으면 DB 가 거부합니다** |
| `snapshot` | 제출 시점의 계산 근거 전체 (§38) |

- **제출 시점을 얼려 둡니다.** 제출 뒤에 새로 천공을 해도 그 회차의 `snapshot` 은 그대로입니다.
- **이미 기성한 공은 다음 회차에서 빠집니다.** 이중 계상이 안 됩니다.
- **반려하면 그 공들이 다시 기성 대상이 됩니다.** 누계에서도 빠집니다.
- 이미 제출한 회차는 다시 제출할 수 없습니다. 되돌리려면 반려해야 합니다.

## 5. 계산 규칙

전부 SQL 결정론적 코드입니다 (§46).

```
물량 공정률 = 완료 계약수량 ÷ 전체 계약수량 × 100        (소수 1자리)
금액 공정률 = Σ(완료 계약수량 × 계약단가) ÷ 계약금액 × 100
기성가능액  = Σ(완료 계약수량 × 계약단가)                 (앞 회차분 제외)
```

- **금액은 원 단위 2자리로 맞춥니다.** 수량(4자리) × 단가(2자리) 를 그대로 두면
  6자리가 되어 표기가 어긋납니다.
- 금액은 API 경계에서 **문자열**로 주고받습니다.
- **물량과 금액이 같은 규칙으로 셉니다.** 한쪽만 날짜로 자르면 같은 화면에서
  물량 10% · 금액 0% 처럼 어긋나 보입니다 (아래 9.1).
- 기간이 필요한 것은 기성이고, 기성 함수가 기간을 받습니다.
- **계약단가가 없는 공은 계산에서 빠지고 그 사실을 WARN 으로 냅니다.** 0원으로 만들지 않습니다.

### 9.1 물량과 금액 공정률이 서로 다른 규칙으로 셀 뻔했다 (고침)

처음 만들 때 금액 공정률만 `construction_date <= 기준일` 로 잘랐습니다.
물량 공정률(기존 `fn_site_progress`)은 완료된 것을 **전부** 세는데 말입니다.

그래서 같은 화면에서 **물량 10% · 금액 0%** 처럼 어긋나 보였습니다.
현장에서는 "시스템이 틀렸다" 로 읽힙니다.

둘을 같은 규칙으로 맞췄습니다. 기간이 필요한 것은 기성이고, 기성 함수가 기간을 받습니다.

### 9.2 금액 자릿수가 어긋났다 (고침)

`계약수량(4자리) × 계약단가(2자리)` 를 그대로 두면 **6자리**가 됩니다.
`10000000.000000` 처럼 나옵니다. 원 단위 2자리로 맞췄습니다.

작은 문제로 보이지만, 기성은 그대로 청구서로 나가는 값이라 표기가 어긋나면 안 됩니다.

### 9.3 §29 불변조건 테스트가 제대로 걸렸다 (설계대로)

기성 테이블을 만들자 PHASE 8 의 "core/share 에 금액 컬럼이 생기면 깨진다" 테스트가
**바로 실패했습니다.** 의도한 동작입니다.

새 컬럼 4개가 **계약금액인지 내부원가인지** 답한 뒤 허용목록에 명시적으로 넣었습니다.
허용목록에 주석으로 그 판단 기준을 남겨 두었습니다.

### 9.4 시험용 시드에 계약단가가 없었다 (고침)

시험사용에서 금액 공정률과 기성이 **계속 0 으로만** 보였습니다.
계산은 맞았지만(단가가 없으니 0), 시험이 되지 않습니다.
시험용 현장에 계약단가 50,000원/m 를 넣었습니다.

### 9.5 남아 있는 주의점

- **기성가능액이 0원이어도 회차를 만들 수 있습니다.** 단가가 없는 공만 있는 경우입니다.
  경고는 회차를 만들 때 함께 나오고, 다른 금액을 제출하려면 사유가 필요하므로
  조용히 잘못될 여지는 막았습니다. 다만 **0원 회차 자체를 막을지는 사람이 정할 일**입니다.
- **설계변경(§38)과 기성의 연결은 아직입니다.** 계약 revision 은 PHASE 2 에 있고
  기성은 현재 계약금액만 봅니다. 회차별로 어느 revision 기준인지 묶으려면
  `payment_certificate.contract_id` 에 revision 을 더해야 합니다. 필요하면 붙이겠습니다.
