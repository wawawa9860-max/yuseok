## 0. 비전문가용 한 줄 요약

**현장에서 통신이 끊겨도 입력이 사라지지 않습니다.**

이번에 두 가지를 했습니다.

1. **레미콘·인원·장비**를 일일입력에 붙였습니다. 다만 §1-4 대로
   **매일 같은 값은 다시 묻지 않습니다.** 인원과 장비는 `[예]`가 미리 눌려 있어
   평소에는 손댈 일이 없고, 바뀐 날만 `[아니오]`를 눌러 **바뀐 것만** 적습니다.

2. **통신이 끊겨도 입력이 되게** 만들었습니다. 저장이 안 되면 휴대폰에 쌓아 두었다가
   통신이 돌아오면 자동으로 보냅니다.

가장 신경 쓴 부분은 **두 번 저장되지 않게 하는 것**입니다.
"보냈는지 확실하지 않아 다시 보냈더니 레미콘 91㎥ 가 182㎥ 가 되는" 사고를 막았습니다.

## 1. 이번에 구현한 기능

### 1.1 §21 인원 — 기본값을 재사용하고 변경만 입력

```
오늘 인원은 기본설정과 동일합니까?     [ 예 ✔ ]  [ 아니오 ]
                                        ↑ 미리 눌려 있다
```

`예` 면 **변경행이 하나도 저장되지 않습니다.** 기본 인원이 그대로 적용됩니다.
`아니오` 를 누르면 직종별 입력칸이 나오는데, **비워두면 기본값을 씁니다.**

기본에 없던 직종(예: 그날만 온 보조원)도 그날만 추가할 수 있습니다.

직종 목록은 시스템이 정하지 않습니다. 현장이 등록합니다.

### 1.2 §22 장비 — 계약방식과 함께

```
천공기   월대(MONTHLY)   1대
펌프카   일대(DAILY)      1대
백호(06) 일대(DAILY)      1대
```

인원과 같은 방식입니다. `동일합니까? [예]` 가 기본이고 변경만 적습니다.
`일대 / 월대 / 기타` 계약방식은 §26 대로 장비마다 지정합니다.

### 1.3 §23 레미콘

```
금일 레미콘 반입량   [ 38 ] m³

공급지연이 있었습니까?   [ 없음 ]  [ 있음 ]
   ↓ '있음' 일 때만
   지연시간   30분 / 60분 / 90분 / 120분
   사유       레미콘공장 / 원도급 / 검측 / 현장조건 / 기타
```

지연시간은 **분 단위로 저장**합니다. §23 이 요구한 대로 나중에 정산증빙·SPECIAL_EVENT 와
연결할 수 있게 하기 위해서입니다.

### 1.4 계획 레미콘량 — 산출근거 방식 그대로

```
(π × 직경²) / 4 × 연장 × (1 + 할증률)
```

π·직경·할증률을 **현장 설계 파라미터에서 읽습니다.** 하드코딩하지 않습니다.
산출근거가 π = 3.14 를 쓰면 3.14 를 씁니다. **시스템이 더 정밀한 값으로 바꾸지 않습니다** (§9).

### 1.5 ★ 오프라인 큐

현장은 통신이 자주 끊깁니다. 세 겹으로 막았습니다.

| 상황 | 대응 |
|---|---|
| 앱이 아예 안 열림 | 화면 파일을 캐시 (PWA) — PHASE 6 |
| 화면은 열리는데 목록을 못 받음 | **마지막 조회 결과를 기기에 남겨 두고 그것으로 연다** |
| 저장이 안 됨 | **기기에 쌓아 두었다가 통신되면 자동 전송** |

통신이 끊긴 상태에서도 지층별 수량을 뺀 나머지를 **기기에서 계산해 보여줍니다.**
다만 그 값이 임시라는 것을 숨기지 않습니다.

```
[WARN] 통신이 안 되어 기기에서 계산했습니다. 지층별 수량은 저장 후 서버가 확정합니다.
```

### 1.6 ★★ 재전송해도 두 번 저장되지 않는다

오프라인 큐에서 **가장 위험한 부분**입니다.
"보냈는지 확실하지 않을 때 다시 보내는" 일이 반드시 생기기 때문입니다.

```
요청마다 client_request_id 를 만들어 붙인다
        ↓
서버가 같은 ID 를 두 번 받으면
        ↓
처음 처리한 응답을 그대로 돌려준다 (다시 저장하지 않는다)
```

실제로 시험했습니다.

```
1차 전송  → 5공 저장, 레미콘 91㎥
2차 전송  (같은 ID) → replayed: true, 같은 daily_work_id
DB 확인   → 레미콘 91㎥ (182 아님), 천공 5공 (10 아님)   ✅
```

**실패한 요청은 기록하지 않습니다.** 같은 트랜잭션 안에서 기록하므로
저장이 롤백되면 기록도 함께 사라져, 고쳐서 다시 보내면 정상 처리됩니다.

## 5. 계산 규칙

| 항목 | 규칙 |
|---|---|
| 계획 레미콘량 | `(π × D²)/4 × 연장`, 소수 3자리 |
| 할증 | `기본량 × 할증률 / 100`, 소수 3자리 |
| 공당 레미콘 | `총량 / 연장`, 소수 4자리 |
| 유효 인원 | `기본 인원`, 당일 변경이 있으면 그 값 |
| 유효 장비 | 위와 동일 |

### 산출근거와 0.005㎥ 차이가 납니다 — 확인이 필요합니다

```
(3.14 × 0.6²)/4 × 2052 = 579.8952

시스템    579.895 + 할증 11.598 = 591.493
산출근거  579.9   + 할증 11.598 = 591.498     ← 중간값을 1자리로 반올림한 뒤 할증

차이 0.005㎥ (0.00085%)
```

산출근거는 **기본량을 소수 1자리로 반올림한 뒤** 할증을 곱합니다.
시스템은 3자리를 유지합니다. 물리적으로는 무의미한 차이지만,
§9 는 "원본의 산출방식을 임의로 바꾸지 않는다" 고 합니다.
**어느 쪽에 맞출지 알려주십시오.** (8-1)

### 이번에 잡은 문제 3건

**① 유효 인원 VIEW 가 그날만 투입된 직종을 버렸다**
`FULL JOIN` 을 잘못 써서, 기본설정에 없는 직종(보조원)이 결과에서 사라졌습니다.
DB에서 직접 확인하다 발견했고 `UNION ALL` 구조로 바로잡았습니다.

**② 통신이 끊긴 채로 입력 화면에 들어가면 앱이 깨졌다**
큐만으로는 부족했습니다. 화면에 들어가려면 천공번호 목록이 필요한데
그걸 못 받아 진입 자체가 실패했습니다. **마지막 조회 결과를 기기에 남기도록** 했습니다.

**③ 계획 레미콘량 기대값을 제가 잘못 계산했다**
`579.902` 로 적었으나 실제는 `579.895` 였습니다. 테스트가 잡아냈고,
확인하는 과정에서 산출근거와의 0.005㎥ 차이(중간 반올림)도 함께 드러났습니다.

## 8. 사람이 직접 확인해야 할 사항

   차이는 0.005㎥ 입니다. 산출근거에 맞추려면 중간값을 소수 1자리로 반올림하면 됩니다.
