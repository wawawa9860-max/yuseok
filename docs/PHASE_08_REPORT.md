## 0. 비전문가용 한 줄 요약

**이번 단계부터 시스템에 진짜 '돈'이 들어옵니다.**

지금까지는 천공번호·심도·수량처럼 계약상대방이 봐도 되는 값만 있었습니다.
이제 단가와 원가가 들어옵니다. 그래서 이번 단계는 기능보다 **차단**에 힘을 썼습니다.

현장관리자가 하는 일은 두 가지뿐입니다.

1. 오늘 쓴 돈을 고르고 금액을 적는다
2. 영수증 사진을 찍는다

**원가 합계도, 단가도, 손익도 현장 화면에 없습니다.**
숨긴 게 아니라 **서버가 애초에 내려주지 않습니다.** DB 권한으로 막혀 있어서
현장관리자 계정으로는 단가 테이블을 조회하는 것 자체가 오류가 납니다 (§29).

그리고 **영수증이 없다고 입력을 막지 않습니다** (§28).
현장에서 영수증을 바로 못 받는 일이 흔하기 때문입니다.
사진 없이 저장하면 `증빙대기`로 남고, 나중에 사진을 붙이면 `증빙완료`가 됩니다.

> 이번 단계에서 **PHASE 7 오프라인 큐의 실제 결함을 하나 찾아 고쳤습니다.**
> 아래 9. 발견된 위험에 적었습니다. 자동 테스트가 아니라 **실제 브라우저**로 찾았습니다.

## 1. 이번에 구현한 기능

### 1.1 §24 투입원가 6개 항목 고정

`노무비 / 장비비 / 유류비 / 잡자재비 / 식대 / 기타경비` — 7번째 항목은 만들 수 없습니다.

이 중 **현장이 입력하는 것은 4개**(유류비·잡자재비·식대·기타경비)뿐입니다.
**노무비·장비비는 본사 단가로 자동계산**되므로 현장에 다시 묻지 않습니다 (§1-2 중복입력 금지).
화면에도 그렇게 적어 두었습니다.

### 1.2 §27 비용 입력 + 사진 증빙 (현장 화면)

```
[비용 · 증빙]
  → [유류비] [잡자재비] [식대] [기타경비]
  → 금액 입력   또는   [지난번과 같음 · 48,000원]
  → [사진 찍기]
  → [저장]
```

`지난번과 같음`은 §1-5(전일값 재사용)입니다. 식대처럼 매일 같은 금액은
**타이핑 없이 3터치로 끝납니다.** 실제 브라우저로 확인한 수치는 7. 에 있습니다.

사진은 `capture="environment"` 라 휴대폰에서 **카메라가 바로 열립니다.**

### 1.3 §28 증빙 상태 — 입력을 막지 않는다

| 상태 | 뜻 | 언제 |
|---|---|---|
| `PENDING_EVIDENCE` | 증빙대기 | 사진 없이 저장 |
| `VERIFIED` | 증빙완료 | 사진이 붙는 순간 (DB 트리거가 자동 전환) |
| `HEAD_OFFICE_REVIEW` | 본사확인 | 영수증 분실 등, 본사가 수동으로 넘김 |

상태 전환은 API 가 아니라 **DB 트리거**가 합니다.
어떤 경로로 사진이 붙어도 상태가 어긋나지 않습니다.

### 1.4 §25 노무비 · §26 장비비 자동계산

```
노무비 = (기본 인원 ± 당일 변경) × 본사 등록단가
장비비 = (기본 장비 ± 당일 변경) × 계약방식별 단가
```

인원·장비는 PHASE 7 에서 이미 받아 둔 값을 그대로 씁니다 (§1-7 재사용).
현장은 아무것도 더 입력하지 않습니다.

**월대(MONTHLY)는 하루치로 환산합니다.** 환산일수(`MONTHLY_WORK_DAYS`)는
시스템이 정하지 않고 **현장 설계 파라미터**로 둡니다. 기본 30일입니다.

```
천공기 월대 15,000,000원 ÷ 30일 =   500,000원/일
                        ÷ 25일 =   600,000원/일   ← 현장이 25일로 바꾸면
```

**단가가 없는 항목은 0원으로 만들지 않습니다.** 그만큼 빠졌다고 알립니다.

```json
{ "code": "RATE_NOT_FOUND", "severity": "WARN",
  "message": "C01: 단가가 등록되지 않은 항목이 3건 있어 그만큼 금액에서 빠졌습니다." }
```

계산근거(`calc_detail`)를 함께 남깁니다. 무엇에 어떤 단가를 곱했는지
사람이 검증할 수 있어야 하기 때문입니다 (§46).

### 1.5 §52 증빙률 — 현장이 볼 수 있는 유일한 원가 관련 지표

```
이번달 증빙  40%      증빙대기  3건
```

**건수만 나갑니다. 금액은 한 푼도 나가지 않습니다.**
자동계산분(노무비·장비비)은 영수증 대상이 아니라 증빙률을 떨어뜨리지 않습니다.

### 1.6 §23 레미콘 송장사진

PHASE 7 에서 남겨 둔 부분입니다. **송장은 원가가 아닙니다.**
영수증과 달리 `visibility='SITE'` 로 남아 현장·본사가 함께 봅니다.

### 1.7 오프라인 큐 — 사진까지 포함

통신이 끊긴 채로 비용 + 사진을 입력하면 **사진 파일까지** 기기(IndexedDB)에 쌓입니다.
통신이 돌아오면 **비용을 먼저 보내고, 그 응답의 비용 id 로 사진을 붙입니다.**
순서가 보장되므로 사진이 미아가 되지 않습니다.

## 5. 계산 규칙

전부 SQL 결정론적 코드입니다. LLM 계산은 없습니다 (§46).

```
노무비   = Σ round(인원 × 일단가, 2)
장비비   = Σ  일대/기타 : round(수량 × 단가, 2)
             월대      : round(수량 × 단가 ÷ MONTHLY_WORK_DAYS, 2)
증빙률   = round(증빙완료 건수 ÷ 수동입력 건수 × 100, 1)
```

- 금액은 API 경계에서 **문자열**로 주고받습니다. 부동소수점 오차를 만들지 않습니다.
- `calc_detail` 안의 단가·금액도 **문자열**로 남깁니다.
  JSON 숫자로 두면 자릿수가 큰 금액에서 클라이언트 쪽 오차가 생깁니다.
- 단가 선택: **현장 전용 단가가 있으면 그것을, 없으면 전사 기본단가**를 씁니다.
  같은 조건이면 `effective_from` 이 늦은 것을 씁니다.
- **환산일수는 시스템이 정하지 않습니다.** 현장 파라미터입니다.

## 6. 권한 규칙

§29 는 3중으로 막습니다. 어느 하나가 뚫려도 나머지가 막습니다.

| 층 | 무엇 |
|---|---|

| 3) RLS | 현장관리자는 **자기 현장 + 본인이 입력한 건**만 |

| 역할 | 비용 입력 | 영수증 업로드 | 증빙률 | 단가 | 원가 합계 |
|---|---|---|---|---|---|
| HEAD_OFFICE | ✅ | ✅ | ✅ | ✅ | ✅ |
| FIELD_MANAGER | ✅ | ✅ | ✅ (건수만) | ❌ `42501` | ❌ `42501` |
| EXTERNAL | ❌ | ❌ | ❌ | ❌ | ❌ (스키마 접근 불가) |

`visibility='HEAD_OFFICE_ONLY'` 로 강제합니다.** 계약상대방 공유로 바꾸려 하면 거부합니다.

## 8. 사람이 직접 확인해야 할 사항

1. **실제 노무 단가와 장비 단가.** 지금 시스템에는 단가가 하나도 없습니다.
   본사가 등록해야 노무비·장비비가 계산됩니다. 등록 전까지는 `RATE_NOT_FOUND` 로 알립니다.
2. **월 환산일수.** 기본 30일로 두었습니다. 회사 관행이 25일이나 26일이면 알려주십시오.
   현장별로 다를 수 있어 현장 파라미터로 만들어 두었습니다.
3. **현장이 입력할 비용 항목을 4개로 좁혔습니다.**
   (유류비·잡자재비·식대·기타경비 / 노무비·장비비는 자동계산)
   현장에서 노무비를 현금으로 직접 지급하는 경우가 있다면 알려주십시오.
   API 는 6개를 다 받으므로 화면만 바꾸면 됩니다.
4. **영수증 분실 시 처리 절차.** 지금은 본사가 `본사확인`으로 넘기게 해 두었습니다.
   실제 회사 규정이 다르면 알려주십시오.
5. **PHASE 7 부터 남아 있는 미결 사항** (변동 없음)
   - 계획 레미콘량을 산출근거 표기(591.498)에 맞출지, 정밀값(591.493)을 쓸지
   - 내역서 H-Pile 규격 `H-300x300*10*15`, 조서 `A61` 29 → 54
   - **R20: 실제 현장관리자 시험사용이 아직 안 되었습니다.** 환경과 안내서는 준비돼 있습니다.

## 9. 발견된 위험

### 9.1 ★ 오프라인 큐가 '동시' 재전송에 뚫려 있었다 (PHASE 7 결함, 고침)

**증상.** 실제 브라우저로 비행기모드 → 통신 복구를 돌렸더니
기타경비 15,000원이 **두 건** 저장되었습니다.

**원인.** 통신이 돌아오는 순간 브라우저의 `online` 이벤트와 앱의 재시도가 겹쳐
같은 요청 ID 가 **나란히** 도착했습니다. 두 요청이 각자
"저장된 응답이 있나?" 를 확인했을 때 **둘 다 '없음'** 이었습니다.
서로 상대가 커밋하기 전이었기 때문입니다.
그 다음 멱등키 기록이 `ON CONFLICT DO NOTHING` 이라 **충돌이 조용히 넘어가고**
중복 저장이 그대로 살아남았습니다.

**PHASE 7 테스트는 이걸 못 잡았습니다.** 순차 재전송(보내고 → 또 보내고)만 시험했기 때문입니다.

**고침.** 조회하기 전에 요청 ID 로 트랜잭션 잠금을 잡습니다.

```sql
SELECT pg_advisory_xact_lock(hashtextextended($1, 0))
```

나중에 온 요청은 앞의 요청이 끝날 때까지 기다렸다가 **저장된 응답을 그대로 돌려받습니다.**
멱등키 기록의 `ON CONFLICT DO NOTHING` 도 없앴습니다. 이제 충돌이 나면 조용히 넘어가지 않고 터집니다.

**검증.** 고치기 전 코드로 되돌려 같은 요청 6개를 동시에 던졌더니
**5건이 중복 저장**되었고, 고친 코드에서는 **1건**입니다.
비용과 일일작업(레미콘) 양쪽에 회귀 테스트를 남겼습니다.

> 이 결함은 레미콘·공수에도 그대로 있었습니다.
> 즉 **레미콘 91㎥ 가 182㎥ 가 되는 사고가 실제로 가능한 상태**였습니다.

### 9.2 영수증 공유 차단이 '조용히' 동작했다 (고침)

`category=RECEIPT` 를 `SHARED_EXTERNAL` 로 바꾸려 하면 막히기는 했지만,
가드가 값을 먼저 `HEAD_OFFICE_ONLY` 로 되돌려 버려서 **거부 메시지가 뜨지 않았습니다.**
공유했다고 착각할 수 있습니다. 순서를 바꿔 **명시적으로 거부**하게 했습니다.

### 9.3 현장관리자는 영수증 파일 행을 볼 수 없다 — 설계상 정상

영수증은 본사전용이므로 현장관리자에게는 **행 자체가 보이지 않습니다.**
그래서 현장관리자가 직접 `stored_file` 에 넣으면 권한 오류가 납니다.

정책을 느슨하게 풀면 §29 가 무너지므로 **'영수증을 붙인다'는 동작 하나만**
통과시키는 함수를 따로 만들었습니다. 자기 현장의, 자기가 입력한 비용에만 붙습니다.
돌려주는 값에도 금액은 없습니다.

### 9.4 남아 있는 주의점

- **비용 목록은 기기에 캐시됩니다** (오프라인에서 `지난번과 같음` 을 쓰기 위해).
  본인이 입력한 본인 현장 금액이고 §29 대상(내부 단가·집계)이 아니지만,
  기기 분실 시 그만큼은 남습니다. 필요하면 캐시를 끄겠습니다.
- **자동계산은 아직 본사가 수동으로 실행합니다.** 일일작업이 저장될 때 자동으로
  돌리는 것이 편하지만, 단가가 없는 상태에서 0원이 쌓이는 편이 더 위험해서
  일부러 본사 승인 동작으로 두었습니다 (§11, §12).
