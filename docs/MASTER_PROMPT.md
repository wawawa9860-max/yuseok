# RF CIP Mobile Field Control V1 — Claude Code 최종 개발 Master Prompt

## 0. 역할

당신은 RF CIP(겹침 CIP) 전문건설회사의 실제 현장 운영을 위한 모바일 현장관리 시스템을 구축하는 수석 소프트웨어 아키텍트이자 풀스택 개발자다.

동시에 다음 관점으로 시스템을 검증한다.

- RF CIP 현장 시공
- 전문건설 공무
- 수량산출·기성·정산
- 모바일 UX
- 데이터베이스
- 보안·권한
- AI 자동화
- 현장 사용자 QA

이 시스템은 일반적인 건설 ERP가 아니다.

50~60대 현장관리자가 휴대폰으로 하루 약 1~3분 내에 입력을 완료하고 마지막에 `[카카오톡 공유]`를 눌러 본사 또는 계약상대방에게 보고할 수 있도록 만드는 것이 최우선 목표다.

---

# 1. 절대 개발 원칙

다음 원칙을 모든 기능보다 우선한다.

1. 복잡한 ERP처럼 만들지 않는다.
2. 현장관리자에게 중복입력을 요구하지 않는다.
3. 최초 현장설정은 상세하게 할 수 있지만 일일입력은 극도로 단순하게 한다.
4. 매일 동일한 값은 재입력시키지 않는다.
5. 기본값과 전일값을 최대한 재사용한다.
6. 정상상태보다 예외상태만 입력하게 한다.
7. 한 번 입력한 데이터를 모든 문서가 재사용한다.
8. AI가 추측해서 계약수량·기성·원가를 확정하지 않는다.
9. 수량과 금액 계산은 결정론적 코드로 처리한다.
10. 계약상대방에게 내부 원가가 절대 노출되지 않도록 서버 수준에서 권한을 분리한다.
11. 기존 데이터를 덮어쓰지 말고 변경이력과 버전을 보존한다.
12. 새 기능 추가보다 현장관리자의 터치 횟수 감소를 우선한다.

새 기능을 추가하기 전에 항상 다음 질문을 한다.

> "이 기능이 현장관리자의 일일 입력시간이나 오류를 실제로 줄이는가?"

그렇지 않으면 기본적으로 추가하지 않는다.

---

# 2. 최종 시스템 정의

제품의 목적은 다음과 같다.

> RF CIP 천공번호 기반 작업·수량·도면·레미콘·공정·기성·원가·정산증빙 통합관리 + 카카오톡 현장보고 시스템

현장관리자의 경험은 다음처럼 단순해야 한다.

> 오늘 뚫은 번호 선택  
> → 레미콘 입력  
> → 인원·장비 변경 확인  
> → 비용이 있으면 영수증 촬영  
> → 특이사항이 있으면 선택/사진  
> → 입력완료  
> → 카카오톡 공유

# 3. 권장 기술 구조

프로토타입도 향후 실제 운영을 고려해 클라우드 구조를 전제로 설계한다.

권장 예시:

- Frontend: 모바일 우선 PWA
- Backend: TypeScript 기반 서버
- Database: PostgreSQL
- Auth: 사용자 로그인 및 역할 기반 권한
- File Storage: 작업도면, 사진, 영수증, 증빙자료
- AI: Claude API 또는 향후 연결 가능한 AI 계층
- Version Control: Private Git repository

특정 클라우드 벤더에 과도하게 종속되지 않도록 데이터 계층을 분리한다.

# 4. 핵심 데이터 원칙 — HOLE_MASTER

모든 시스템의 단일 기준은 `HOLE_MASTER` 즉 천공번호 MASTER다.

수량산출서와 작업도면을 서로 다른 원장으로 관리하지 않는다.

두 문서는 동일한 `HOLE_MASTER`를 서로 다른 방식으로 보여주는 VIEW여야 한다.

전체 관계:

계약내역
+
수량산출서
+
작업도면 / 전개도
↓
HOLE_MASTER
↓
실제 시공
↓
작업일보
천공일지
작업도면 진도
수량실적
레미콘
공정률
기성가능액
특이사항
정산증빙

# 6. 가장 중요한 수정 — 지반조건 설계

지반조건은 시스템이 고정된 조합으로 강제하지 않는다.

현장마다 지층조건이 다르기 때문이다.

예:

현장 A

```text
토사
+
풍화암
```

현장 B

```text
토사
+
풍화암
+
연암
```

현장 C는 또 다른 조합일 수 있다.

따라서 다음 구조로 개발한다.

---

# 7. GROUND_TYPE — 현장별 지층종류 설정

본사 또는 최초 현장설정 권한자가 해당 현장에서 사용할 지층종류를 직접 만든다.

예:

```text
SITE A

G01 토사
G02 풍화암
```

또는:

```text
SITE B

G01 토사
G02 풍화암
G03 연암
```

향후 필요 시:

```text
G04 경암
G05 전석층
G06 자갈층
G07 기타
```

등을 사용자가 추가할 수 있도록 한다.

시스템 자체는 특정 지층명을 필수값으로 강제하지 않는다.

---

# 8. 지반조건은 "조합 + 깊이" 구조

`토사+풍화암` 같은 텍스트 하나만 저장하지 않는다.

각 천공번호에 지층별 계획 깊이를 구조화해서 저장한다.

예:

A-001

```text
총 계획심도 = 20.0m

토사      0.0 ~ 12.0m = 12.0m
풍화암   12.0 ~ 20.0m = 8.0m
```

다른 현장:

B-001

```text
총 계획심도 = 24.0m

토사      0.0 ~ 10.0m = 10.0m
풍화암   10.0 ~ 19.0m = 9.0m
연암     19.0 ~ 24.0m = 5.0m
```

반드시:

```text
각 지층 깊이 합계 = 총 계획 천공심도
```

가 되는지 프로그램에서 검증한다.

불일치하면 저장 전에 경고한다.

중요:

# 10. 지반조건 범위 일괄설정

현장에서 수백 개 천공번호를 하나씩 입력하게 해서는 안 된다.

반드시 범위 지정 기능을 만든다.

예:

```text
천공번호
A-001 ~ A-030

지반조건
토사 12.0m
풍화암 8.0m

총 심도
20.0m

[범위 적용]
```

다음 범위:

```text
A-031 ~ A-065

토사 10.0m
풍화암 7.0m
연암 4.0m

총 심도
21.0m
```

사용자가 범위를 지정하면 해당 번호들에 일괄 적용한다.

---

# 11. 수량산출서와 동일한 값이 최우선

지반조건의 계획값은 시스템이 임의 계산하거나 추정하지 않는다.

기준 우선순위:

1. 계약 수량산출서
2. 승인된 설계/작업도면
3. 본사 또는 현장 담당자의 승인 입력

수량산출서에 다음과 같이 되어 있다면:

```text
A-001 ~ A-030

토사      360m
풍화암    240m
```

30공 기준 동일조건이라면 범위 적용 시:

```text
공당 토사      12m
공당 풍화암     8m
```

처럼 환산할 수 있으나,

반드시 사용자에게 계산 결과를 보여주고 확인을 받은 후 저장한다.

수량산출서가 공별로 서로 다른 값을 가지고 있다면 원본 값을 그대로 적용한다.

# 12. 수량산출서 가져오기

향후 Excel 업로드 기능을 고려한다.

가져오기 과정:

```text
수량산출서 업로드
↓
열 구조 분석
↓
천공번호 확인
↓
지층 종류 후보 확인
↓
계획심도 확인
↓
계약수량 확인
↓
미리보기
↓
사용자 승인
↓
HOLE_MASTER 반영
```

AI는 열 이름과 구조를 해석하는 보조 역할만 한다.

계약수량 변경을 자동 확정하지 않는다.

---

# 13. 작업도면 연결

작업도면의 천공번호와 HOLE_MASTER의 `hole_no`를 1:1 연결한다.

사용자는 도면에서 천공번호 위치를 확인할 수 있어야 한다.

가능하면:

```text
A-001
A-002
A-003
...
```

번호별 도면 좌표 또는 도면상의 참조정보를 저장한다.

도면은 다음 상태를 보여준다.

- 미시공
- 금일완료
- 기존완료
- 보류
- 변경
- 확인필요

색상은 UX 단계에서 결정하되 상태 의미가 명확해야 한다.

# 14. 도면과 수량산출서 자동 검증

다음 자동검증을 구현한다.

### 천공번호 누락

```text
작업도면에 A-041 존재
HOLE_MASTER에 A-041 없음
→ 본사 경고
```

### 반대 누락

```text
HOLE_MASTER A-042 존재
작업도면에 없음
→ 본사 경고
```

### 중복번호

```text
A-043이 두 번 존재
→ 저장 차단 또는 본사 확인
```

### 계획심도 불일치

```text
수량산출서 = 20.0m
도면/MASTER = 21.0m
→ 본사 확인
```

# 15. 실제 지반조건은 계획과 분리

계획 지반조건과 실제 천공 시 확인된 조건을 동일 필드에 덮어쓰지 않는다.

예:

```text
PLANNED

토사 12m
풍화암 8m
```

실제:

```text
ACTUAL / FIELD NOTE

토사 예상보다 깊음
풍화암 시작심도 차이
연암 출현
```

현장관리자가 매 공마다 실제 지층 연장을 상세 입력하도록 강제하지 않는다.

일일 현장입력은 단순해야 한다.

기본 질문:

```text
계획 지반조건과 다른 특이사항이 있었습니까?

[없음]
[있음]
```

`있음` 선택 시:

```text
[토사구간 차이]
[풍화암구간 차이]
[연암 출현]
[예상 외 지층]
[지하수]
[기타]
```

그리고:

```text
[사진]
[음성메모]
[간단메모]
```

를 사용할 수 있게 한다.

---

# 16. 실제심도 입력도 예외 방식

계획심도와 실제심도가 같다면 현장관리자가 다시 입력하지 않는다.

질문:

```text
계획심도와 동일합니까?

[예]
[아니오]
```

예 → 계획심도를 실제심도로 자동 적용.

아니오 → 해당 천공번호만 실제심도 입력.

# 20. 지층별 일일 생산량 자동집계

HOLE_MASTER의 계획 지반조건을 이용해 금일 선택된 번호의 지층별 수량을 자동집계한다.

예:

오늘 A-031 ~ A-040 완료 시:

```text
금일 10공

토사       112.0m
풍화암      74.0m
연암        26.0m

총 천공량   212.0m
```

사용자가 다시 토사/풍화암/연암 수량을 직접 입력하지 않는다.

단 실제 설계변경이나 정산에 사용할 확정수량은 승인 절차를 거친다.

# 21. 기본 인원

현장별 기본값을 저장한다.

예:

- 현장관리자
- 천공기 장비기사
- 펌프카 기사
- 백호(06) 기사
- 천공기 작업반장
- 천공기 부반장
- 기타

일일 질문:


# 36. 공정률

기본적으로 두 가지를 사용한다.

### 물량 공정률

```text
누적 완료 계약수량
/
전체 계약수량
× 100
```

### 금액 공정률

```text
누적 시공 인정금액
/
현재 계약금액
× 100
```

보조지표로:

- 공수 기준
- 총 천공연장 기준
- 지층별 천공량

을 조회할 수 있게 한다.

# 37. 기성

```text
기성가능액 ≠ 실제 제출 기성
```

으로 구분한다.

실제 기성 제출은 본사 승인이 필요하다.

```text
풍화암 8m
```

- 설계변경 전
- 설계변경 후
- 실제시공

```text
수량산출서 지층합계 불일치

지층별 길이 합계
!=
총 계획심도

완료 Hole인데 천공일지 없음

완료 Hole인데 실적수량 미반영

계약수량 초과

외부 사용자의 PRIVATE_COST 접근시도
```

- 특이사항 분류
- 작업일보 문장 생성

- 불일치 후보 탐지

- 변경계약 금액
- 원가 확정
- 설계변경 확정
- 사용자 권한
- 데이터 삭제
- 외부 발송

# 53. 개발 시작 지시

지금 바로 전체 기능을 한 번에 코딩하지 마라.

먼저 현재 프로젝트 디렉터리와 기존 코드가 있다면 전체 구조를 분석하라.

기존 코드가 없다면 새로운 프로젝트의 최소 구조를 설계하라.

그 후 `PHASE 1`부터 시작한다.

PHASE 1에서 우선 다음을 확정한다.

```text
1. DB schema
2. 사용자 역할
3. HEAD_OFFICE_ONLY 원가 권한
4. SITE_MASTER
5. CONTRACT_MASTER
6. HOLE_MASTER 기본구조
7. GROUND_TYPE
8. GROUND_PROFILE
9. Revision 구조
10. 파일 Storage 구조
```

특히 `GROUND_TYPE`과 `GROUND_PROFILE`은 특정 지층 종류를 하드코딩하지 말고 현장별 사용자 정의 방식으로 구현하라.

지반조건의 최종 기준은 해당 현장의 승인된 수량산출서이며, 수량산출서와 다른 값을 AI가 임의로 만들어서는 안 된다.

PHASE 1 완료 후 코딩 결과와 구조를 비전문가도 이해할 수 있게 설명하고 다음 단계 진행 명령까지 제공하라.
